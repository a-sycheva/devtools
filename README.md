## Технологический стек проекта

### Языки и платформы
- **Java 25 LTS** — основной язык разработки
- **Gradle 8.x** — система сборки (через Gradle Wrapper)

### Инструменты качества кода
- **Checkstyle** — статический анализ стиля кода
    - Конфигурация: `config/checkstyle/checkstyle.xml`
    - Запуск: `./gradlew checkstyleMain`
- **JUnit 5** — фреймворк тестирования
    - Запуск: `./gradlew test`

### CI/CD
- **GitHub Actions** — автоматическая проверка PR
    - Checkstyle на каждый коммит
    - Тесты на каждый коммит
    - Конфигурация: `.github/workflows/`

### Правила кода
- Стиль: Google Java Style Guide (через Checkstyle)
- Коммиты: Conventional Commits (`feat:`, `fix:`, `docs:`)
- Ветки: `feature/DVT-X` для задач, `master` — основная
- Pull Request: обязателен для слияния в master

### Порядок импорта

<pre>
До:

import java.util.ArrayList;
После:
import java.util.ArrayList;
import java.util.List;
Почему:Java Convention требует располагать импортированные имена в порядке сортировки ASCII, который упрощает поиск импортов.
Источник: https://google.github.io/styleguide/javaguide.html#s3.3-import-statements
</pre>

### Лишняя строка перед // (более 1)

<pre>
До:
import java.util.List;


// нарушение: лишняя пустая строка
После:
import java.util.List;

// нарушение: лишняя пустая строка
Почему: Java Convention несколько подряд идущих пустых строк допускаются, но никогда не являются обязательными (и не поощряются). Наличие лишних пустых строк может ухудшат читаемость кода при code review, а также увеличивает вертикальный размер кода.
Источник: https://google.github.io/styleguide/javaguide.html#s4.6-whitespace
</pre>

---


### if без {}

<pre>
До:   
if (student != null)
studentList.add(student);
После:
if (student != null)
{
studentList.add(student);
}
Почему: Java Convention требует, чтобы Фигурные скобки соответствовали стилю Кернигана и Ритчи для непустых блоков и блокоподобных конструкций, что улучшает читаемость кода, создает единообразие. Проще понимать логические блоки.
Источник: https://google.github.io/styleguide/javaguide.html#s4.1-braces

</pre>

---


### Длинна строки больше 100

<pre>
До:   
public void i_just_want_to_have_method_with_very_long_method_name_that_exceeds_one_hundred_twenty_characters_and_with_problem_in_it() {
После:
public void method_with_problem_in_it()
Почему: Длинные строки затрудняют чтение в редакторе и при code review. Java Convention регламентирует длинну строки не более 100 символов (с возможностью переноса на другую строку в указанных в разделе Line-wrapping случаях)
Источник: https://google.github.io/styleguide/javaguide.html#s5-naming
</pre>

## Code Review Checklist

Используйте этот чеклист для само-ревью перед запросом ревью у ментора:

### Функциональность
- [ ] Код решает поставленную задачу полностью
- [ ] Обработаны граничные случаи (null, пустые данные, экстремальные значения)
- [ ] Обработка ошибок реализована корректно

### Тесты
- [ ] Добавлены тесты для нового функционала (или обновлены существующие)
- [ ] Все тесты проходят локально: `./gradlew test`
- [ ] Покрыты позитивные и негативные сценарии
- [ ] JaCoCo coverage ≥ 80% для нового кода

- [ ] Имена переменных, методов и классов отражают назначение
- [ ] Нет дублирования кода (DRY principle)
- [ ] Checkstyle проходит без ошибок: `./gradlew checkstyleMain`
- [ ] Нет закомментированного кода или отладочного вывода (`System.out.println`)

### Документация
- [ ] README обновлён (если добавлена новая функциональность)
- [ ] Публичные методы имеют JavaDoc (если применимо)
- [ ] Примеры использования актуальны
- [ ] Runbook обновлён (если изменились команды запуска/проверки)

### Производительность и безопасность

### AI-промпты и сравнение ассистентов

---

#### Промпт 1: План решения

**Задача:** Посчитать общее количество уроков, общее количество пройденных уроков и общее количество оставшихся уроков у нескольких менти.

**Контекст:** Java 25, есть класс Mentee, содержащий в себе количество пройденных уроков completedLessons,
и общее число уроков totalLessons.   

**Ограничения:** Использовать массив и цикл while 

**Ожидаемый результат:** план из 3-5 шагов, объяснение "почему именно так", НЕ пиши код — я реализую сам

**Критерии успеха:** рассчитанное количество оставшихся уроков неотрицательно и не превышает общее количество уроков

**AI-1 (DeepSeek):**

<pre>
План решения (3-5 шагов)
1.	Создание и наполнение массива:
Объяви и инициализируй массив типа Mentee. Сразу заполни его несколькими объектами (например, 3-5 штук), чтобы было с чем работать. У каждого менеджера должны быть заданы totalLessons (общее число) и completedLessons (пройдено).
2.	Инициализация счетчиков:
До начала цикла создай три переменные (int), в которых будешь хранить итоговые суммы:
	o	totalSum — общее количество уроков у всех менти.
	o	completedSum — общее количество пройденных уроков.
	o	remainingSum — общее количество оставшихся уроков.
Присвой им начальное значение 0.
3.	Организация цикла с предусловием (while):
Создай индексную переменную (например, i = 0). Условием цикла поставь i < длина_массива. Внутри цикла на каждой итерации обращайся к текущему элементу массива (mentee[i]).
4.	Аккумуляция данных и проверка:
В теле цикла последовательно выполни три действия:
	o	Прибавь totalLessons текущего менти к totalSum.
	o	Прибавь completedLessons текущего менти к completedSum.
	o	Главный нюанс: вычисли разницу для текущего менти (totalLessons - completedLessons) и сразу прибавь её к remainingSum. Это самый надежный способ избежать ошибок с отрицательными значениями на промежуточных этапах.
	o	Не забудь в конце тела цикла увеличить индекс i на 1.
5.	Анализ результата (пост-обработка):
После завершения цикла у тебя будут три итоговые суммы. Проверь, что remainingSum действительно равна totalSum - completedSum. Если это так, значит, подсчет выполнен верно. Отрицательных чисел в remainingSum по итогу быть не может, если данные на входе корректны.
Почему именно так?
	•	Почему массив? Задача явно учебная, направленная на понимание строгой типизации и работы с индексами, прежде чем переходить к более удобным коллекциям. Массив дает жесткую структуру, где размер фиксирован.
	•	Почему цикл с предусловием (while)? Это требование нужно, чтобы ты потренировался явно управлять индексом. В отличие от for-each, здесь ты сам следишь за условием продолжения работы и шагом, что полезно для понимания работы итеративных алгоритмов "под капотом".
	•	Почему шаг 4 (аккумуляция) важен? Суммирование оставшихся уроков должно происходить на уровне каждого отдельного менти, а не вычитанием общих сумм на промежуточном этапе. Например, если у одного менти 5/5, а у другого 0/5, сумма остатков (0 + 5) будет равна 5. Если бы ты сначала сложил общие уроки (10), потом пройденные (5) и вычел их (10 - 5), ты бы тоже получил 5. Математика сработала бы, но логика пошагового накопления данных здесь нагляднее.
</pre>

**Определение:** абстрактная вычислительна машина для запуска Java-приложений скомпилированных в байт-код (.class). **Контекст использования:**  JVM выступает исполняющей средой для Java-приложений на любом устройстве, где установлена JVM. JVM исполняет не инструкции на языке программирования Java, а байт-код, записанный в файлах формата class.

**Пример:**  Сначала компилятор javac проверяет синтаксис и преобразует ваш код в байт-код — промежуточное представление, понятное JVM.Если компиляция прошла успешно, JVM начинает исполнять байт-код.

#### Integrated Development Environment (IDE) - Интегрированная среда разработки

**Определение:** программное обеспечение, которое объединяет широко используемые инструменты разработки в одно самодостаточное приложение, предоставляя интегрированную среду кодирования для инженеров-программистов.

**Контекст использования:**  В отличие от текстового редактора, IDE понимает структуру проекта, показывает ошибки в момент ввода и предлагает исправления. Здесь пишется код, запускаются тесты, просматриваются логи и выполняется отладка.

**Пример:** Открой Main.java — IDE создаст компактный void main()

**Источник:** https://www.jetbrains.com/pages/static-code-analysis-guide/what-is-an-ide/

---

#### Software Development Kit (SDK) - Инструмент разработки программног обеспечения

**Определение:** набор инструментов, необходимых для разработки приложения для конкретной программной платформы.

**Контекст использования:** Java SDK (JDK) содержит необходимые для разработки на  Java инструменты: компилятор, отладчик, утилиты библиотеки.

**Пример:**  Если устанавливаешь JDK через мастер создания проекта в IntelliJ IDEA, SDK появится только внутри IDE.

**Источник:** https://www.jetbrains.com/help/idea/sdk.html#supported-sdks

#### (Git) Repository — Репозиторий

**Определение:** набор ссылок вместе с базой коммитов, содержащей все коммиты, которые достижимы из этих ссылок.

**Контекст использования:** репозиторий нужен, чтобы хранить все версии проекта (код + историю) и управлять ими через ветки/теги, обеспечивая быстрый доступ, операции Git и, при необходимости, совместное использование базы объектов.

**Пример:** GitHub — это веб-сервис для хостинга Git-репозиториев, который добавляет множество функций для совместной работы.

**Источник:** https://git-scm.com/docs/user-manual#def_repository

---

#### Commit — Коммит

**Определение:** : конкретная точка в истории состояния Git-проекта. Слово «коммит» часто используется в Git там же, где другие системы контроля версий используют слова «ревизия» или «версия».

**Контекст использования:** Коммит по сути является "снимком" текущего состояния проекта и позволяет как использовать его для внесения изменений в проект (слияния), так и при необходимости вернуться к предыдущему состонию проекта.

**Пример:** Команда git commit создает новый коммит, который фиксирует все изменения, находящиеся в индексе, и добавляет его в историю локального репозитория.

**Источник:** https://git-scm.com/docs/user-manual#Documentation/user-manual.txt-commit

---

#### Branch — Ветка

**Определение:** линия разработки. Самый последний коммит в ветке называют вершиной (tip) этой ветки. На эту вершину указывает голова ветки (branch head) — это ссылка, которая двигается вперёд, когда в ветке появляются новые коммиты (то есть когда продолжается разработка).

**Контекст использования:** Ветки позволяют одновременно работать над разными компонентами разрабатываемого проекта без угрозы нарущить его целосность и функциональность.

**Пример:** Откройте Git → Branches… или нажмите Ctrl+Alt+Shift+Backtick → выберите Git Branches → New Branch…. Введите feature/DVT-3, поставьте галочку Checkout branch и нажмите Create — IDE переключится на новую ветку, статус-бар внизу справа покажет feature/DVT-3.

**Источник:** https://git-scm.com/docs/user-manual#Documentation/user-manual.txt-branch

#### Pull Request (PR) — Запрос на слияние

**Определение:** предложения по объединению изменений кода в проект; базовая функция сотрудничества GitHub, позволяющая обсуждать и анализировать изменения перед их объединением. Это помогает командам работать вместе, своевременно выявлять проблемы и поддерживать качество кода.

**Контекст использования:** позволет осуществить безопасное слияние, провести код-ревью, провести проверки CI/CD, показывает вносимые изменения

**Пример:** Хороший PR содержит цель, краткое описание изменений, список проверок (run/test/debug) и ссылки на Evidence Pack

**Источник:** https://docs.github.com/ru/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests

---

#### Merge - Слияние

**Определение:** перенос содержимого другой ветки (возможно, из внешнего репозитория) в текущую ветку.

**Контекст использования:** при слиянии изменений из одной ветки в другую происходит проверка на конфликты и только после их решения возможно безопасное слияние.

**Пример:** Оформляем PR по feature/DVT-3 и выполняем merge в master (на GitHub)

**Источник:** https://git-scm.com/docs/user-manual#Documentation/user-manual.txt-merge

#### Checkstyle - Checkstyle

**Определение:** Инструмент разработки, помогающий программистам писать код на Java, соответствующий стандартам кодирования.

**Контекст использования:** автоматизирует процесс проверки проверки кода на соответсвие принятому стандарту, выявляет нарушения и указывает их местоположение.

**Пример:** для запуска проверки кода проекта (без учета тестов) используется команда ./gradlew checkstyleMain

**Источник:** https://checkstyle.org/

---

#### Debugger - Отладчик

**Определение:** часть IDE, позволяющая анализировать поведение вашего приложения во время выполнения, выявлять проблемный код и поэтапно изолировать источник проблемы.

**Контекст использования:** позволяет остановить выполнение программы на заданной строке (breakpoint) и пошагово проходить код, наблюдая изменение переменных, вычислить выражение в данной точке остановки программы.

**Пример:** студент запускает Debug (Shift+F9) и использует Step Over (F8) для прохождения итераций

**Источник:** https://www.jetbrains.com/help/rider/Debugging_Code.html

---

#### Breakpoint - Точка остановки

**Определение:**  специальный маркер, который приостанавливают выполнение программы в определенной точке. Точки останова могут быть простыми, например, приостановка работы программы при достижении какой-либо строки кода, или включать в себя более сложную логику, такую как проверка на соответствие дополнительным условиям, запись в журнал и так далее).

**Контекст использования:** указывает точку остановку выполяемой программы для дальнейшего анализа ее поведения

**Пример:** установлен breakpoint на строке цикла в методе calculateTotalProgress

**Источник:** https://www.jetbrains.com/help/rider/Using_Breakpoints.html

### Категория: Процессы и практики

#### Code Review — Код ревью, проверка кода

**Определение:** процесс, в ходе которого кто-то, помимо автора(ов) кода, проверяет этот код. Необходимо для поддержания качества кода и продуктов.

**Контекст использования:**  способствует обмену опыта в команде, выработке и поддержанию общих стандартов написания кода, поддержке его функциональности.

**Пример:** Согласно State of DevOps Report 2024, команды с обязательным Code Review выпускают в production код с на 85% меньшим количеством критических багов и на 40% быстрее доставляют новые фичи благодаря распределению знаний.

**Источник:** https://google.github.io/eng-practices/review/?utm_source=chatgpt.com

---

#### Runbook

**Определение:** набор документированных процедур, описывающих, как выполнить тот или иной процесс, будь то запуск, остановка, отладка или устранение неполадок в конкретной системе.

**Контекст использования:**  в рамках курса - содержит пошаговые инструкции разрешения проблемных ситуаций

**Пример:** в проекте devtools Runbook содержится в README.md

**Источник:** https://docs.gitlab.com/user/project/clusters/runbooks/?utm_source=chatgpt.com

---

#### Continuous Integration and Continuous Deployment(CI/CD) — непрерывная интеграция и доставка/развертывание

**Определение:** набор методов и инструментов, разработанных для улучшения процесса разработки программного обеспечения путем автоматизации сборки, тестирования и развертывания, что позволяет быстрее и надежнее выпускать изменения в коде.

**Контекст использования:** автоматическая проверка и доставка изменений позволяет быстрее находить ошибки, ускорить выпуск версий, снизить вероятность нарушить функциональность проекта

**Пример:** GitHub Actions — это встроенная CI/CD-платформа от GitHub, которая позволяет настроить автоматические задачи (workflows) прямо в репозитории.

**Источник:** https://github.com/resources/articles/ci-cd

## Вопросы по сложным терминам

### Вопрос 1: Инструмент сборки

**Задача:** понять на примере Gradle какую функцию и на каком этапе работы с проектом выполняет инструмент сборки

**Контекст:** термин встречается в курсе начиная с DVT-2

**Ограничения:** с одной стороны, есть понимание, что Gradle это "что-то, что всё собирает", с другой не хватает глубинного понимания процессов.

**Ожидаемый результат:** понимаю, что именно делает Gradle на каждом шаге работы с проектом: скачивает зависимости, компилирует код, запускает тесты, делает отчёты, собирает JAR, знаю какую команду Gradle запускать в типичных ситуациях, понимаю, где на диске лежат результаты работы Gradle

**Критерии успеха:** понимание разницы между командами build, test, run, расположения результатов работы команд, способность правильно выбрать команды перед перед коммитом, публикацией/релизом, на CI.

---

### Вопрос 2: (Gradle) Artifact

**Задача:** понять, что такое артефакт в Gradle и как он появляется на практике

**Контекст:** термин встречается при изучении инструментов сборки и CI, GitHub Actions есть пункт "upload artifacts", также термин встречается при работе с зависимостями.

**Ограничения:** необходимо разобраться в отличиях понятия артефакт в конктексте собрки проекта и в контексте зависимостей; почему артифакт иногда это каталог (директория), а не файл; какие команды Gradle создают артефакты и где их искать.

**Ожидаемый результат:** понимаю два основных смысла артефакта в Gradle: как результат сборки, который создаётся задачами сборки, и как часть зависимостей.

**Критерии успеха:** могу показать конкретный файл/папку и уверенно сказать: “это артефакт”, и какая Gradle-задача его создала, вижу разницу между артефактом моего проекта и артефактом зависимости.
